# Flue Research Report — is j2 using flue the way that makes most sense?

## Sources
- Flue docs (flueframework.com): concepts/agents, guide/{workflows,tools,durable-execution,subagents,sandboxes,observability}, api/agent-api, sdk/{overview,agents}, getting-started/quickstart.
- **Real flue source, checked out at `/home/richs/repos/flue`** (a full monorepo — `packages/runtime/src/*`), which let me verify claims in ADR-0002/0006/0011/0013 against actual code rather than docs summaries.
- j2 source: `packages/orchestrator/src/{actor.ts,flue-client.ts,durability.ts,registration.ts}`, `packages/adapter/src/adapter.ts`, `deploy/harness-dev/agent.ts`, `examples/coding/workflows/coding.ts`, `CONTEXT.md`, ADR-0002/0006/0009/0011/0012/0013.
- j2 pins `@flue/sdk` at **`1.0.0-beta.5`** (`packages/orchestrator/package.json`).

## (a) Is j2 leveraging flue features it currently reimplements?

**Partly — with one real gap and one likely-outdated assumption.**

1. **Submission-level retry/timeout — flue already has this, j2 layers its own on top.** `defineAgent()`/`AgentProfile` in real flue takes a `durability: { maxAttempts, timeoutMs }` field (`packages/runtime/src/agent-definition.ts`), and the runtime (`runtime/agent-submissions.ts::reconcileInterruptedSubmission`) already does exactly what the brief wants "absorbed": distinguishes `completed`/`aborted`/`exhausted_retry_budget`/`exceeded_timeout`/`interrupted_after_input_application`, redispatches an unconfirmed provider call **at most once** (never re-runs a completed tool), and settles with a typed terminal error. Defaults: `maxAttempts=10`, `timeoutMs=3_600_000` (`agent-execution-store.ts`). j2's Machine-level `retriesLeft`/`spendRetry`/`hasRetryBudget`/`retryOrEscalate` (`coding.ts`) is a **second, coarser retry loop** that re-invokes the whole `agentRun` actor on `agent.fault` — largely duplicating what flue's own submission reconciliation already does for infra faults. The brief's decision 5 (a defaulted knob, not context) has a natural home in flue's `durability` config on the agent definition; j2 could route infra-fault retry through that instead of Machine-context bookkeeping, and let `agent.fault` fire only on flue's own terminal outcome.
2. **"No-signal nudge" is genuinely NOT something flue gives you on the surface j2 uses** — see (b). Keep it.
3. **Cancel/abort: j2 reimplements "abandon and hope durability reaps it" because of the pinned SDK version.** `packages/orchestrator/src/actor.ts` line 105 and `flue-client.ts` explicitly say "flue exposes no cancel primitive." That was true at beta.5. **Flue added `client.agents.abort(name, id)` / `POST /agents/:name/:id/abort` in `1.0.0-beta.8`** — a first-class terminal outcome (`SubmissionAbortedError`, `abortRequestedAt`), distinct from failure, that also flushes queued work. **This directly contradicts a stated ADR-0002 assumption** and is an easy, real win: bump the dependency and replace the abandon-and-reap `cancel()` in `flue-client.ts` with a real abort call.
4. **Offset/stream reconnection: j2 hand-rolls it; flue's post-beta.5 client is built for exactly this.** j2's `flue-client.ts` manually iterates `flue.agents.stream(name, id, {offset, signal})` and checkpoints on `tool_start`. In beta.8+, flue replaced the raw stream-session model with `client.agents.observe()`/`client.agents.history()` — a **materialized-snapshot, reconnect-and-continue-from-offset API** purpose-built for "resume after restart." This is the same primitive j2's `durability.ts`/`reattachAgentRuns` is manually reconstructing. Worth prototyping against the newer SDK before finalizing "offsets 100% j2-internal" — the internals may get simpler, not just the workflow-facing API.
5. **Structured/forced output ("finish"): flue's own mechanism is real but not reimplementable by j2 on the agent path** — this is the load-bearing constraint, covered in (b).

## (b) Does flue offer a cleaner primitive for "one turn, exactly one workflow tool" than the MCP-adapter arrangement?

**No — and this is the most important finding to lock in before the redesign proceeds.** Flue *does* have a built-in "the turn ends by calling exactly one tool" primitive: `finish`/`give_up` (`packages/runtime/src/result.ts`), auto-injected whenever a caller passes `{ result: schema }` to `session.prompt()`/`.skill()`/`.task()`, complete with its own **nudge on silence** (`buildResultFollowUpPrompt`, sent when the LLM ends a turn without calling either). That is exactly the shape the brief wants.

But verified in `session.ts`: this is wired only into ad-hoc `prompt/skill/task` calls made from **inside a workflow's `run()`** (an ephemeral, non-addressable, non-continuing session keyed by a fresh `runId`). The **durable, continuing agent HTTP path** (`POST /agents/:name/:id`, what j2's Actor drives via `instanceId`) runs through `runPersistedContextInput`, which calls `withCallOverrides({ tools: [], model: undefined, ... })` — **no `extraTools`, no result schema, ever** on that path. This is the exact disjoint-session finding ADR-0006 already made (verified now against source, not just docs): the session-storage key is `[instanceId, harness, session]`, and a workflow's first key component is a server-generated `runId`, so a named/continuing session can never be a `finish`-forcing session.

**Conclusion for the redesign: do not expect to delete the MCP-adapter/registration-table machinery in favor of "just use flue's finish tool."** It's structurally blocked by flue's own session-key composition, confirmed current. The MCP-menu-of-workflow-events arrangement (ADR-0011/0013) is j2's necessary invention *because* flue's native single-tool-forced-completion feature is unavailable on the one surface (continuing agent) j2 needs. Any API-redesign proposal should treat "MCP adapter mediates the state's event menu" as settled physics, not an open question.

**Bug worth fixing regardless of the redesign:** ADR-0013's own code sample —
```ts
tools: [await connectMcpServer({ url: `${env.J2_ADAPTER_URL}/mcp/${id}` })]
```
— and the identical snippet mirrored in `deploy/harness-dev/agent.ts`'s header comment, **omit the required first positional `name` argument**. The real signature is `connectMcpServer(name: string, options: McpServerOptions)` (`packages/runtime/src/mcp.ts`). This also matters for the tool-naming the LLM sees: adapted MCP tools are named `mcp__<name>__<toolName>` — so whatever server-key j2 picks becomes literally visible to the model as its tool-call name. Confirm this before wiring a real Harness against real flue.

**What ADR-0013's core enabling claim gets right (verified true in source):** `defineAgent(initialize)` really is re-run **on every submission**, not once per instance (confirmed by `agent-definition.ts`'s own doc comment and by `agent-submissions.ts::openAgentSubmissionSession` calling `ctx.initializeRootHarness(agent)` per admitted submission). So the "list_changed is unnecessary" claim and the whole "Harness names its own iid, Adapter never has to learn which turn is live" design are solid and should not be re-litigated.

## (c) Is same-instance-id conversation continuity being used idiomatically?

**Yes.** Flue's continuity model has no separate "resume" API — reusing `(agentName, instanceId)` on the agent path *is* resumption; `openAgentSubmissionSession` always resolves the same default session for a given id. CONTEXT.md's "Instance ID" entry and j2's `iid()` helper fit this exactly — flue treats instance ids as opaque caller-chosen strings, imposing no shape requirement, so deriving them hierarchically is a pure j2 convention layered on top, not friction against flue's model. One operational constraint: submissions to one instance id are attempt/lease-fenced (effectively serialized) in flue's runtime, so j2 must never dispatch two concurrent prompts to the same id — j2's per-role id suffix (coder vs reviewer get different ids even inside one shared Workspace) already avoids this correctly.

## (d) Flue constraints shaping the proposed simplifications

- **Ambient endpoint (decision 3):** No flue obstacle. The client is constructed from a `baseUrl` per call site; nothing in flue's wire model demands per-tool-call endpoint threading in workflow-author code. Purely a j2 wiring choice.
- **Retries absorbed (decision 5):** Real overlap with flue's `durability.maxAttempts/timeoutMs`, but **it doesn't cover the whole ask.** Flue's retry is for *infra/provider faults where output wasn't durably persisted* — it will never fire for "the agent responded but didn't call any menu tool," because from flue's perspective that's a normal, completed turn. So even after leveraging flue's native retry, **j2 still needs its own separate "no-signal, nudge" loop** — two different fault classes; the redesigned API should not conflate them into one knob.
- **Offsets host-side (decision 2):** Squarely aligned with flue's own direction — flue's send/stream/observe model is offset-based and reconnect-first by design. If anything, flue is nudging toward doing *more* of this through its own client (`agents.observe()`) rather than j2 hand-rolling `tool_start`-cadence checkpointing — an implementation simplification opportunity.
- **MCP-in-Sandbox (ADR-0013) + disjoint-session (ADR-0006):** the two real flue-shaped walls. Both independently re-verified against current flue source. Treat as fixed constraints.

## Flag: assumptions in the brief/ADRs that flue's actual design contradicts

- **"flue exposes no cancel primitive"** (ADR-0002, repeated in `actor.ts`/`flue-client.ts` comments) — **false as of flue `1.0.0-beta.8`** (j2 pinned to `beta.5`). `client.agents.abort()` / `POST /agents/:name/:id/abort` exists and is a proper terminal outcome. Recommend the redesign explicitly decide whether to bump the SDK dependency.
- **`connectMcpServer({ url })` call shape in ADR-0013 and `deploy/harness-dev/agent.ts`** is missing the required `name` argument per the real signature — a latent bug to fix whenever this is wired against real flue.
- Everything else load-bearing in ADR-0002/0006/0011/0013 (disjoint agent/workflow sessions, per-submission `defineAgent` re-init, `list_changed` unnecessary, MCP tool naming, instance-id-is-resumption) checked out true against the actual flue source.
